Configuring DBLog Agents

Tip: Typically you need to separate the Analog and Digital tags that you want to log into different DBLog agents, due to their unique logging requirements.

The DBLog configuration dialog is divided into the following sections:

The top checkboxes that determine the general operation of this agent:

  • The Enable checkbox (the BOOLEAN start slot), which allows you to start/stop this agent from logging the listed tags.
  • The Disable on standby checkbox (the BOOLEAN disableOnStandby slot), which allows you to disable this agent, when its Agent Server is part of a cluster and is in standby node - to prevent the logging of DUPLICATE tags.

  • The String logging checkbox (the BOOLEAN strLog slot), when enabled logs the tag values as Strings and not numeric values; this also allows you to log other string slots (this will log the first 79 characters).

    Note: While DBLog agents typically log Numerical and Digital values or bits, they can be configured to convert ALL values to Strings, by checking the String logging checkbox - but this is NOT recommended for general use, since it requires MORE SPACE to store String values compared to Numerical values and this can also cause formatting problems.

Then the selected Logging method determines which parameters are required and when the list of tags are logged, as follows:

  • Log all on interval: all the listed tags are logged at the specified Logging interval regardless of whether they have changed or not and regardless of their quality.

    Tip: This method is typically used when logging Analog values.

  • Log on change: only the tags that change are logged, typically when their value or quality status changes.

    IMPORTANT: To prevent this logging method from logging the tags when their quality status changes, add the following registry value and set it to 1: DisableOnQualityChangeLogging.

    Note: Only this method allows for the logging of historical putslots.

  • Log all on change: all the listed tags are logged if ANY tag value changes.

    Note: Tags are ONLY logged when a value of ANY listed tag changes.

  • Log all on trigger value -> zero: all the listed tags are logged when the value of the specified Trigger tag goes to zero.
  • Log all on trigger value -> non-zero: all the listed tags are logged when the value of the specified Trigger tag leaves zero.
  • Log all on trigger any value change:all the listed tags are logged when the value of the specified Trigger tag changes value.

IMPORTANT: When selecting the Log all on interval method, do NOT add more than 5000 agents to the DBLog agent, otherwise ALL the logged values are ALWAYS be dumped to a .SQL file and not be logged directly to the database, since the total number of logged values exceeds the maximum queue size (5000). More detail:

This agent provides a queue of values waiting to be logged to the specified database (or buffer), when the number of items in this queue exceeds 5000, the currently unlogged transactions are dumped to a .SQL file in the C:\ProgramData\Adroit Technologies\Adroit\Configurations\Default\Work folder.

These .SQL files can be manually loaded into SQL Enterprise manager and executed to “catch up” this data. Each file name uses the following format: DBLogAgentName_Y_M_D_H_M_S.sql.

Tip: You can split DBLog agents up to share the load of the agents being logged.

Then the Tag list, which is sorted alphabetically, allows you to specify and configure the tags that are logged according to the specified Logging method, as follows:

Either manually browse in the required tags, by using the button to both browse in the tag and add it to the list, which is sorted alphabetically - so it may not be added to the end of this list.

Tip: You can also use the button to add a blank row to this list and then type in the required tagA fully qualified named value in Adroit (agentName.slotName)..

Or configure this list from a CSVComma Separated Value file containing data, which consists of a number of fields in one or more rows, in which the different fields (values) are typically separated by commas. editor, as follows:

  • Manually add the first tag to the Tag List (since you cannot export an empty list).
  • Click the Export... button to export this as a CSV file and open the current CSV editor for you, such as Microsoft Excel, so you can populate this list will all the required tags.
  • Save this CSV file.
  • Click the Import... button and browse for this required CSV file to import the configured tag list.

Specify the required VALUE deadband, in the Deadband column of either the CSV file or the Tag list, as follows: specify the MINIMUM Value which the value being logged must EXCEED for it to be logged. Since, if the change in value is LESS than this value then this value is NOT logged.

IMPORTANT: When logging DIGITAL values, ensure that this Value deadband is 0, otherwise NO values will be logged.

 

Then you can specify both the OLE DB database and the table name in which these tags are logged, as follows:

Note: While these fields specify SQL, you are able to connect to any OLE DB database.

SQL connection string: the required OLE DB connection string to the database where these tag values are to be kept (the VARSTRING connection slot). 

Note:

If you specify global, the Global OLE DB connection string of the Agent Server is used, which is specified in the Adroit Config Editor.

  • Typically, you can launch this tool from the Desktop shortcut.
  • Select the Agent Server Configuration Welcome menu item.
  • Select the Advanced Agent Server Configuration option.
  • At the bottom of the dialog, the Global OLE DB connection field is available for you to specify this connection string.

SQL table name: the name of the table in this database to log this data, which is Adr_DBLog by default (the STRING tableName slot).

 

Tip: If you want basic trending and/or to summarise your data in a structured way then, we recommend that you install the Adroit Report Suite and specifically the General Reports report pack, which includes standard reports on the DBLog agent data.

Important:  If the computer, on which SQL Server was installed, was renamed, then SQL Server may need to be re-installed.

If the computer was renamed after installing SQL Server, then SQL Server must be re-installed, to function correctly.

Run the following check:

  • Execute the following T-SQL (Transact-SQL) script in SQL Server Management Studio: SELECT @@SERVERNAME
  • If the resulting server name is different to the actual name of the computer, then the name of the computer has been changed after SQL Server was installed, so you need to reinstall SQL Server.

Lastly, the Housekeeping section allows you to specify how long, in days, that you want to store your logged data, as follows:

By default housekeeping takes place at the turn of midnight, however you can control the hour of the day for housekeeping by adding and configuring the HousekeepingHour registry setting.

Note: These housekeeping settings apply to the database table that a DBLog agent logs to. More details:

DBLog Housekeeping configuration examples:

  • DBLog1 writes data to Table1 and is configured with no housekeeping:

So housekeeping will NOT run on Table1, as expected.

  • DBLog2 writes data to Table2 and housekeeping is configured:

So the specified housekeeping WILL run on Table2, as expected.

  • DBLog3 and DBLog4 writes data to the same table Table34 -
  • DBLog3 is configured with no housekeeping AND
  • DBLog4 is configured with 30 days housekeeping:

So Housekeeping WILL run on Table34 as per DBLog4’s housekeeping configuration for this SHARED table.

  • DBLog5 and DBLog6 writes data to the same table Table56 -
  • DBLog5 is configured with 30 days housekeeping AND
  • DBLog6 is configured with 90 days housekeeping:

So Housekeeping will run on Table34 as per DBLog5’s housekeeping configuration and the data older than 30 days will be deleted, since the SHORTEST housekeeping period is always used as this is the period that is reached first for this SHARED table.

This depends upon the storage capacity you have available for your database and how useful this data becomes to you the older it gets.

Specify the maximum number of days to keep records for (the INTEGER housekeepDays slot).

Note1: A value of 0 disables this housekeeping functionality, provided NO OTHER DBLog agents log to the specified table that have configured housekeeping!

Note2: By design, one additional day's worth of data is kept for you.

If necessary, when performing housekeeping you can also specify an OPTIONAL Backup folder to backup the old data to, before it is deleted from the table (the VARSTRING housekeepFolder slot).

IMPORTANT1: Please ensure that the specified folder exists on the computer where SQL is installed (this is NOT the Agent Server computer when using a remote SQL Server) or housekeeping will not happen!

IMPORTANT2: ALSO ensure that the specified folder name does NOT contain SPACES or housekeeping will ALSO not happen!

IMPORTANT3: ALSO ensure that the database has the necessary permissions needed to add these files to this specified folder or housekeeping will ALSO NOT HAPPEN!

Note1:This path is specified relative to the computer where SQL is installed (this is NOT the Agent Server computer when using a remote SQL Server).

Note2: Leaving this field empty disables this backup functionality.

When this backup folder is being used each DBLog agent creates a daily flat cabinet (.CAB) file of the data that is to be deleted (by the SHORTEST Housekeeping setting if multiple DBLog agents log to the same table).

These files are self-extracting SQL scripts, which you need to manually execute against the required SQL database, in order to import your data.

PLEASE NOTE: It is up to you to manage the files stored in this folder yourself.

Once the DBLog Agent has been configured and enabled, it creates table/s in the specified database with the following fields:

  • id: a unique indexing identifier
  • dt: the Timestamp of the logged value
  • Tagname: the name of the tag being logged
  • Value:– the value of the tag being logged
  • Quality: an indication of whether value of this logged tag was good or bad.

This agent ALSO creates the Adr_DBLog_AgentDetails table, which contains all the agents referenced by all DBLog agents to provide more details about these referenced agents, which can be used to provide more context about them for reports.

This table is updated when: the agent is started; or when its tag list is changed; and unconditionally every morning at 01h00 and this table contains the following fields:

  • ID – integer key: a unique indexing identifier
  • Owner – varchar(255): the DBLog agent name for future use to remove entries owned by the agent
  • AgentName – varchar(255): the name of the agent of the tag being logged
  • AgentDescription - varchar(255): the description of the agent being logged
  • AgentType – varchar(255): the agent type of the tag being logged
  • TagName – varchar(255): the tag being logged
  • TagDescription – varchar(255): a description of the tag being logged; always equal to AgentDescription unless agent type is Marshal whereupon it contains the description of the bit
  • Units - varchar(255): for Analog agents only
  • OffText - varchar(255): for Digital and Marshal agents only
  • OnText - varchar(255): for Digital and Marshal agents only
  • RawMin - float: Raw (device-scale) minimum scaling limit for Analog agents only
  • RawMax - float: Raw (device-scale) maximum scaling limit for Analog agents only
  • EngMin - float: Engineering minimum scaling limit for Analog agents only
  • EngMax - float: Engineering maximum scaling limit for Analog agents only
  • LoLo - float: Low-low alarm level for Analog agents only
  • Lo - float: Low alarm level for Analog agents only
  • Hi - float: High alarm level for Analog agents only
  • HiHi - float: High-high alarm level for Analog agents only

Note: If you do not intend to make use of this table then you can prevent this table from being created by all of your DBLog agents, by adding the following registry value and setting it to 0: DumpAgentDetailsEnabled.

The Adr_DBLog_Housekeeping_Config table is also created, simply contains a list of all DBLog agent tables requiring housekeeping, which is required to perform this housekeeping without affecting the logging operations of the DBLog agents.
