About Alarming Strategies

BEFORE any agent is alarmed it is RECOMMENDED to create and use an Alarming strategy.

An alarming strategy is simply a set of guidelines or a plan to optimise the configuration of the alarming of agents. Also once created it can easily be transferred and adapted for other projects, if required.

Although this may seem unnecessary to take the time to create such a strategy, as with all planning a little time spent in the beginning is richly rewarded by the end of a project. An alarming strategy is necessary for the following reasons:

  1. It simplifies the initial engineering of the alarming.
  2. It ensures that the required alarms will be sent to the desired destinations and can be correctly filtered.
  3. It eliminates confusion, with regard to the often complex routing of alarms.
  4. It prevents the re-engineering of the alarming, if a mistake is detected after the initial alarming configuration has been performed.

Although this is not a definitive description of creating an alarming strategy, the following issues need to be considered when this is being formulated:

  1. Display of Alarms: Determine which alarm destinations will be used i.e. how the alarms will alert the relevant plant personnel and the standards that are to be used for each destination.

For instance: capitalization rules; the number and width of columns to display etc. In this way it is possible to ensure a consistent look and feel for the displayed alarms, which will assist the plant personnel in responding to alarms quickly.

  1. Filtering of Alarms: An alarm priority can be specified for each agent, so that alarm agents can filter out all the alarms generated by low priority agents, if necessary.

However, since this alarm priority is tag-specific rather than alarm-specific, it cannot be used as an efficient alarm filtering mechanism, for instance if we only want to display a sub-set of the alarms configured for an agent.

The only mechanism in Adroit that can achieve this is to use an Alarm list as a destination and use the alarm viewer filtering mechanism.

  1. Routing of Alarms: Construct a routing schematic, which details the alarm destinations that are to be used by each route, in each Alarm agent:

Note: By default Operator Action Behaviours are routed along route 1, specify the LMOperatorAction registry value if you need to specify another alarm route.

  1. Decide on the number of agents to alarm per Alarm agent - there is no limitation for this.
  2. Decide on required number of alarm routes to use.

Note: Do not use route 0 or 1 as these are predefined Adroit system routes.

  1. Decide which routes need to be logged persistently i.e. to the Eventlog and which should be sent to DbAccess for access from 3rd party MES applications etc.

Note: Ensure that the alarms generated from a single agent are routed using the SAME alarm agent. For instance, the Hi and HiHi alarms of an Analog agent must both be routed using the SAME Alarm agent.

  1. Decide which alarms must be sent as SMSShort Message Service is a service (protocol) for sending short text messages to and from mobile phones., by allocating a route for SMS's. Although you probably will need to have more than one route that uses a Notify agent or Command agent as a destination.
  2. Decide which alarm types will go on which route – IMPORTANT if using more than one Alarm agent in this strategy – you can't alarm a tag on 2 different Alarm agents. For instance, considering the following two alarms of an Analog agent called Tank_level:
    • The Hi alarm could be sent along route 2 for an operator to act on (via an alarm window).
    • The HiHi alarm actually sends an SMS to someone.

Therefore, if your strategy involves using different Alarm agents to split other various sections of our plant up, these routes will be different but end in the same destinations e.g. same alarm list.
