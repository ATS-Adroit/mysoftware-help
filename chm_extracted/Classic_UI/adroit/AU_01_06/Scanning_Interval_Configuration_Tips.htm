Scanning Interval Configuration Tips

A scanning interval can be specified in the Scan rate (ms) field when a tagA fully qualified named value in Adroit (agentName.slotName). is being scanned to a FEDfront-end device, which is a device that is accessed directly by the user, such as a PLC or RTU.. This is used to specify the time, in milliseconds, which will elapse before this value is communicated to or from this device. For details on scanning tags, see How to scan a tag or Scanning tags for general scanning information.

Note: This field should ONLY be specified when configuring POLLED devices, since event-based or TELEMETRY devices do not use setting when communicating.

Please consider the following recommendations when configuring this scanning interval:

  1. It is good practice to make your scan-interval longer, for polled drivers, because this minimises the queuing of tasks to be performed by the driver.

Scan-tasks are created by Adroit (not the driver) whenever the scan-interval expires. Once a scan task has been created it is given to the driver, where it joins the queue of existing tasks.

Hence when scan-times are too short, the queue of existing scan-tasks to performed by the driver increases, which cause configuration-tasks, such as the adding or removal of scan-points or the starting/stopping of the devices, to arrive at the back of this same queue.

If the scan-intervals are configured to be longer, then the queue of scan-tasks is reduced, so that the configuration-tasks can be dealt with sooner.

Note: The length of the task queue also affects control actions or writes, to the device, which are usually not prioritised to the front of the queue.

By slowing the scanning sufficiently, pauses can be created in which nothing is happening, which can be filled by a fast-scanning task.

However there is a limit to the number of fast scanning tasks that can be accommodated i.e. if a large amount of fast scanning is required then more sluggish scanning is required too.

Therefore, as scan tasks are added, the scanning intervals need to be constantly adjusted and increased to cater for the increased traffic. For details on grouping scanned data together with similar scanning intervals, see Scanning Optimization.

  1. Drivers interlock all communications on a communication resource (e.g. COM1) so that it is not possible for the driver to do 2 polls at the same time on a port, but is possible to do 2 polls at the same time on 2 different ports.

Note: In this example RTU (Remote Terminal Unit) could also mean any other front-end device, such as a PLC.

This means that the request to a RTU #1 has to complete before the request for data from RTU #2 starts. But if RTU #1 responds very slowly, the driver may timeout before this response has been given and so will query RTU #2 for a response but receive the response from RTU #1 instead. Hence the driver loses synchronization as a result of this confusing traffic.

Although this problem can be prevented by making the scan-times longer, it would be better to make the timeouts longer to accommodate any late responses, since then no performance is lost when the RTU responds within the required time.
