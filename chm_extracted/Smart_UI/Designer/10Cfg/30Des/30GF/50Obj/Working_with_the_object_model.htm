the object model

The object model enables you to enhance your existing wizards by adding SCADASupervisory Control And Data Acquisition, used to monitor and control an industrial plant or process and its related equipment. configuration to them. Its primary function is to help save engineering time when you are creating bulk objects, such as items of equipment, which require similar SCADA configuration.

What the object model does for you?

It saves you SCADA engineering time when creating object templates or instances:

  • It lets you reliably duplicate objects that have all or most of their SCADA configuration pre-configured, such as scanning, logging and alarming.
  • The typical objects you create will be items of equipment, like pumps or motors, including anything that you have already created to represent in a wizard.
  • You can add one or more attributes, searchable strings or identifiers that you can use to filter or group the objects, that you deploy, in the Context View window.
  • You may also use the Object Model Template Export and Import utility to import or export one or more of your existing Object Model Templates in a proprietary TEF (Template Export File) file format.
What the object model does NOT do for you?

The object model will not help you to:

  • Create a graphical representation of the object, because it requires a working instance of a wizard.
  • Create the SCADA configuration required by this object, as it requires that all the necessary agents are already assigned in the selected wizard instance and that these agents are correctly configured.
How does the object model work?

Up to now, wizards have let you create animated graphical representations of your objects, such as pumps and motors, which you can duplicate as needed in your SCADA process and then link them to the required process values.

  • The primary function of the object model datasource is the mass reuse of objects, where each object has a graphical component, much like the existing wizards, and a SCADA component which incorporates the scanning, alarming and logging of tags.
  • Essentially, it is a bulk SCADA configuration tool, which lets you standardise the configuration of your equipment.
  • It was mostly left up to you to manually implement for each object wizard instance of the SCADA configuration, such as the required scanning, alarming and logging.
  • You can use the object model datasource to implement the required SCADA configuration for each of your objects (i.e. a fully configured instance of a wizard) and create a template, which specifies both the graphical representation and the required SCADA configuration for this object.
  • Tip:  If you have an object with identical wizards and different graphical representations, you can associate other wizards to this object template.
  • To reliably duplicate pre-configured objects, you can implement instances of this template,
    • which creates and configures the necessary agents required by this object,
    • and also provides the required graphical representation.
  • The template and object instances only reference the wizard and do not encapsulate it.
    • When you drop an object instance on a graphic form, it is the wizard instance that provides the SCADA configuration.
    • You can interact with this wizard instance as usual.
    • If you update the original wizard, you can update this wizard instance if you want to.
  • Note:  It is also possible for an object template to incorporate one or more existing object templates within this template, for instance by adding a faceplate to a pump. So you need to create your lower-level or commonly used object templates first.

An example of a practical scenario:

Consider an industrial plant having a large number of similar pumps made by the same manufacturer and each pump has some characteristics that differ, such as the pump’s power calibration. The engineer creates a wizard that provides a graphical representation of each pump, using the following steps:

  1. Implement a wizard and create the necessary SCADA configuration for each pump, such as its required scanning, logging and alarming.
  2. Test that the SCADA configuration is working correctly.
  3. Now, create a template from this working wizard, ensuring that the characteristics that are different between the pumps are substitutable.
  4. Using this template, the engineer creates multiple instances of the pump, changing each of their different characteristics as needed.
  5. As a result, each instance of the pump would have their individual scanning, logging and alarming pre-configured.
What do you need before you can create an object template?

You need a configured working instance of a wizard where you have fully configured the required SCADA configuration. The instance is then available for duplication to all your other objects.

Important:  Take the necessary time to test that the wizard has been correctly configured and is working optimally. Ensure that it can be scanned, logged and alarmed correctly. Be aware that any mistakes or omissions will be duplicated.
So, take care!

Take a wizard on a graphic form, one that is working as required and use it to create a new template.

  • The template must incorporate the graphical components of the wizard, along with any substitutions that it uses, and including the SCADA configuration.
  • You can now create numerous instances of each that will create their own unique tags and can be scanned, logged and alarmed, as specified by the template.
  • For example, if you have created a wizard for a pump, you can create a template for the pump that displays the pump, all its relevant values on a graphic form and also creates the required tags and performs the necessary scanning, logging and alarming.

Important:  Creating templates is a task for advanced users who are fully aware of how their SCADA system (Agent Server) is configured. However, creating the template instances is a lot easier.

Note:  A template always refers to an existing wizard. However, if the referenced wizard is deleted or modified, it does not affect the existing template instances that have already been added, it will only affect the instances that you add later.

Managing your object model templates

You can also create child templates so that you can create a template that uses an existing template.

  • These child templates form the basic, or commonly used, building blocks from which you can add to your other templates.
  • You may also use the Object Model Template Export and Import utility to import or export one or more of your existing Object Model Templates in a proprietary TEF (Template Export File) file format.
  • You do not have to create all the object model templates that you require since the object model datasource can install global or system templates, which are available immediately after installation.
  • These global or system templates are added to the Enterprise Manager category folders Datasources > Object Model > Templates > System.
  • To assist you and your users in selecting the appropriate template, both the global templates and the templates that you create can be further classified into sub-folders, for ease of reference.
  • By default, all templates created by users are added to the Enterprise Manager category folders Datasources > Object Model > Templates > User.

You can add specialised sub-folders and move your templates into these folders.

  • You can do this within the Enterprise Manager, or you can use Windows Explorer.
  • When next the SmartUI Server loads it acquires the folder structure as you have created it. You can, therefore, create a workflow that suits your project best.
  • If you do choose to use Windows Explorer, these templates are stored in the following physical location on the SmartUI Server computer: C:\ProgramData\Adroit Technologies\Adroit\SmartUI\Configurations\Default\ObjectModel\Templates
  • Note:  This path assumes that you are using the Default configuration, otherwise replace "Default" with the name of your currently active Configuration, which you can retrieve from the Configurations page of the SmartUI Config Editor.

 

  • While you are not permitted to move or delete the global or system templates and their sub-folders in the Enterprise Manager category folders Datasources > Object Model > Templates > System in the Designer, you can do so in Windows Explorer. The next time the SmartUI Server loads, it updates the template folder structure.
  • These templates are stored in the following physical location on the SmartUI Server computer: C:\ProgramData\Adroit Technologies\Adroit\SmartUI\ObjectModel\Templates
Creating an object model template

To start, use a wizard instance on a graphic form that you have already configured, which is working as required and is already configured with the necessary SCADA configuration (i.e. the scanning, logging, and alarming) plus any other agents that the object needs.

  1. For detailed steps to create a template, see Creating or Editing an Object Template.
  • Important:  You need to ensure that the required SCADA configuration of this wizard instance is exactly what you require, because it will be copied verbatim and will include all errors or mistakes if any.
  • Tip:  If you keep the identical substitution names as those you have used in the wizard, this makes it easier to implement your instances, as you will only need to configure these substitutions once. If you don’t use the same substitutions, you should specify unique substitutions during both the SCADA and Graphical Substitution stages.
  1. Next, create a template from the wizard, which incorporates the graphical components of the wizard (and any substitutions that it uses), along with the SCADA configuration that you specify. Now, you can create numerous instances of each that will create unique tags and can be scanned, logged and alarmed, as specified by the template.
  • Note:  To create an object template, you need to be fully aware of how your SCADA system (Agent Server) is configured.
  1. Once you have created an object template, and any other instances that you create using this template, the referenced wizard will provide the graphical components and uniquely configure the SCADA configuration for the process values that you have specified for each object.
    • For detailed steps to create an instance, see Creating an Object Instance.
  1. When complete, you can either deploy an instance immediately or you can partially, or fully, deploy this object later.
    • For detailed steps to deploy an instance later, see Deploying an Object Instance.

Defining attributes for your templates and objects

  • When creating an object template or an object instance, you can add one or more attributes, searchable strings, or identifiers that you can use to filter or group the objects that you deploy in the Context View window.
  • These provide user-friendly terms that you can use to identify the object, such as equipment Type, whose value may be ‘motor’ or ‘valve’ or some other type or perhaps the power specification, such as 'kWh' and then specify the required value for each Type object.
  • Once you have created the object instance, you can view both the template- and object-specific attributes and values that have been defined and configured for this object.
  • For detailed steps to view the instance attributes, see Viewing the defined attributes of an Object Instance.
How the Context View window augments the object model

The Context View tool windowtool windows are dockable windows, which provide several arrangement options to increase the size of the Design workspace window used for designing graphic forms., logically groups or organises the deployed objects according to their defined attributes, so that they can be easily located and searched.

  • All the objects that have identical attributes are added as separate groups or 'contexts'.
  • The grouping created is hierarchical, and objects are further classified or grouped according to their specified values of this attribute. This lets you identify which objects have the same values and those which have been assigned a particular attribute.
    • If, for example, an attribute defines the power rating for equipment:
      • You would see all your equipment that has the same power rating.
      • If an attribute assigns the manufacturer, you could see all the equipment made by each manufacturer.
  • By defining common attributes for your deployed objects, the Context View window can become a handy tool in managing not just your deployed objects, but also your entire process.
  • Important:  These contexts are automatically generated and cannot be edited, indicated by the red key icon in the context list at the bottom of this window.

For more information, see Context View tool window.

Organising your objects

You can edit the Default context to create your own logical organisation of your objects and other data, by either:

  • Adding the necessary hierarchy of nodes , or
  • if you have implemented Alarm Management, you can import your existing hierarchy of categories as nodes , with or without the agents that are associated with their configured incidents.
  • For detailed steps to editing the default context, see Editing the Default context.
  • Creating an object instance in a node of the Default context can be particularly useful when its name and substitutions use a predefined naming convention that specifies the context in which the instance is created.
  • For detailed steps to creating context-sensitive instances, see Creating contextually sensitive object instances.
