Database Behaviour

The Database Behaviour functionality provides you with an easy method of accessing data that has been returned after running a database query and the result displayed on a control or vector placed on a graphic form.

The database query can be processed in two ways:

  1. A Database Query in the Spider Configuration
  • Although you can currently use queries on a graphic form, the setup is normally done in the Spider Configuration.
  • Warning:  This setup is sometimes quite complex.
  • Requires you to be a relatively advanced or experienced user to successfully set up a query to link it to a control or vector to achieve the desired result.
  1. A Database Query using the Database Behaviour provides the following advantage
  • It removes the complexity you would encounter in the spiders and silks to create and successfully execute queries in an OLEDB Data Source.
  • It automatically determines the spider configuration required for a selected query and query type, and also its target control or vector.
  • It creates the relevant spiders and silks in the background that are required to execute a query successfully.
  • Note:  Previously, you were required to go to the Spider Configuration workspace to manipulate spiders and silks manually.
  • It also lets you easily edit a current spider configuration which is related to executing a query.
  • Includes deleting the entire configuration, not leaving any spiders or silks behind that might have to be managed manually.

Configuring a database query

Current behaviours work on the principle that you must first select a control or vector, which displays the relevant behaviour types available for the selected control or vector. You can select and configure a behaviour required for the control or vector.

The above process is not suitable for all Database Behaviour action scenarios and requires modification to allow for a slightly different flow for the following reason:

It is possible that without a Database Behaviour action, you may use the current configuration options available with spiders and silks, to successfully execute a query without interacting with a control or vector at all.
For example, an Update, Delete or Insert query can be triggered through the following methods, Propagate at Startup or Trigger from event (for example, the Form.Click event).

The Database Behaviour is always selectable regardless of whether a control (or vector) is used or not.

Let’s go through each step required to configure a new Database Behaviour.

STEP 1: Launching a Database Behaviour

The Database icon is always available for selection, regardless of whether a control or vector is selected. One of the following two scenarios can be used to create a new Database Behaviour:

  1. As with other behaviours, you may select the relevant control or vector to display the resultant dataset from a query.
    • Click the Behaviours toolbar menu item then select the Database icon in the Behaviours ribbon of the SmartUI Designer.
    • Alternatively, click the Smart Tag on the selected control or vector, then select the Database Behaviour option from the selection list of available behaviours.
  2. If control or vector is not selected in the graphic form itself, you can still select the Database icon in the Behaviours ribbon.
    • You use this option to execute a query type that does not return a resultant dataset to a control or vector on a graphic form.
    • For example, an Insert query only does database-side processing and does not return a dataset to the DataGridView control.
STEP 2 (Optional): Select the appropriate Apply to property option to apply to the query dataset

Note:  If no control or vector is selected before opening the Database Behaviour dialog, the property list won’t be available, and this step becomes irrelevant, then proceed to step 3.

The following default properties are available, depending on the type of properties contained in the selected control or vector. You can change the selected property, if necessary:

  1. For a control with a DataSource property, such as the DataGridView control, this property is selected by default.
    • The DataSource property can consume an entire data table but is only appropriate for SelectQuery types.
    • All other properties using simple types, such as int, string or bool, are also included in the property list.
    • Complex property types are excluded.
  2. For a control with both a DataSource and a DisplayMember property, such as a Listbox or Combobox control.
    • The DataSource property is selected by default.
    • All other properties using simple types, such as int, string or bool, are also included in the property list.
  3. For a control that does not contain a DataSource property.
    • All properties using simple types, such as int, string or bool, are included in the property list.
    • An appropriate default property is selected depending on the selected control and its property list.
    • For example, the Text property is selected by default for a Label or Button control.
  4. If a control has no DataSource property and no properties using simple types.
    • The Apply to property option is hidden.
    • You can still trigger the selected query from an event on a control.
STEP 3: Select the Server to retrieve your resultant query dataset

Similar to the Query Spider in the Spider Configuration:

  • The Default Server placeholder name and all available servers are listed for selection in the Enterprise Manager of the SmartUI.
  • The Default Server is selected as the default option.
STEP 4: Select the OLEDB Data Source to retrieve your resultant query dataset

Similar to the Query Spider in the Spider Configuration:

  • All the configured data sources of type OLEDB for the server, selected in the previous step, are listed for selection.
  • You will encounter one of the following scenarios, when:
No OLEDB data sources are configured for the selected server.
  • A New Data Source button is available.
  • Click the button to create a connection to the required source of data.
  • You can create a new OLEDB data source without closing the behaviour dialog and then reopening it to continue.
One or multiple OLEDB data sources are configured for the selected server.
  • The list of data sources available for connection are listed alphabetically, but none are selected by default.
  • You may still click the New Data Source button to create a connection to a required source of data.
  • A Connection Details button is available to view the details of the currently selected OLEDB data source.
When a valid data source has been selected.
  • The Query Type option becomes visible.
STEP 5: Select the Query Type you want to use to retrieve your resultant query dataset

Similar to the Query Spider in the Spider Configuration:

  • All available query types are listed in the Query Type selection list for the selected OLEDB Data Source.
  • No query type is selected by default.
  • In the selection list, each query type displays the number of currently configured queries for that specific type, in brackets, after the query type name, e.g. SelectQuery (3).
  • You will encounter one of the following scenarios, where:
None of the available query types have any queries configured for them for the selected OLEDB data source.
  • After selecting a query type, a New query button is available that you may click to create a new query for the selected query type.
One or more of the available query types has one or more queries configured for them for the selected OLEDB data source.
  • Each query type that has queries configured for it displays the number of configured queries, in brackets, after the query type name, e.g. SelectQuery (3).

  • After selecting a query type that has one or more queries configured for it, a New query button becomes available.
Two additional things will occur:
When a valid query type has been selected.
  • The Query Name option becomes visible.
For all query types other than the SelectQuery type.
  • The Apply to property option at the top of the Database Behaviour dialog is hidden because this option is irrelevant for non-SelectQuery types.
  • All other query types only do database-side processing, with no resultant dataset to display.
  • The reason is that only a SelectQuery returns viewable data (i.e. a dataset), that can be used to display database records on a control or vector.

 

STEP 6: Select the Query Name you want to execute

After you’ve selected the query you want to run from the available list of queries, or a new query you have created, you will have access to a View query button that may be used to view the actual SQL query statement associated with the query.

Related to the selected query, you will encounter one of the following scenarios:

  • The selected control or vector has a DisplayMember property.
  • Field Name option is made visible.
  • For example, with a Listbox or Combobox control, only one data field record can be displayed.
Query type SelectQuery selected.

  • The selected control or vector does not have a DisplayMember property.

    STEP 7 (Optional): Select the Field Name you want to display

    For one of the scenarios in the previous step where the Field Name option is made visible.

    • When selecting a field name, Database Behaviour only displays records from that field in the selected control or vector.
    • Only relevant to queries of type SelectQuery.
    STEP 8 (Optional): Do you want to be prompted for confirmation before the query is executed?

    The Confirm Action option only applies to queries that are not of type SelectQuery.

    • By default, the non-compulsory Confirm Action option is not selected.
    • If Confirm Action is selected, the Database Behaviour prompts you to confirm that the query must be executed.
    STEP 9 (Optional): Do you want the execution of the query be triggered from an event?

    The Trigger from event option applies to all query types.

    • By default, this non-compulsory Trigger from event option is not selected.
    • If not selected, the Database Behaviour is triggered through Propagate at Startup.
    • If selected, you can choose from the available selection list of Event Objects and Event Names, to trigger the behaviour.

    Configuring query parameters

    It is possible to create queries where not all the parts of the query are known at the time of creating it. It is especially true that you might want to generate dynamic query results by supplying or inserting different values into the WHERE clause of the query just before the query is executed.

    • To help facilitate this process, the Query Spider currently provides inputs for parameters that can be driven either by a default value or from the output silk of another spider, such as a Property Spider of the Text property of a Textbox or Label control.
    • Warning:  This type of configuration is currently a manual process and requires an advanced understanding of spiders to correctly and successfully achieve this.
    • The Database Behaviour solves this by giving all types of users, from beginners to advanced, access to this level of configuration without having to know and understand how to do it manually.

    The following steps guides you through a simple process to follow and shows you how to configure the source inputs for each parameter in the query:

    STEP 1: Selecting a query that contains parameters

    Access to the setup of parameters for a query starts with the selection of a query that contains parameters.

    • When a valid query is selected, the Parameters tab becomes visible.
    • By default, an error icon indicates that errors exist, implying that values must be provided for the parameters present in the query.

    The values that must be provided should consist of the following types:

    1. The source of the input for the parameter.
      • Component Property is selected by default.
    2. The value of the input for the parameter.
      • The parameter is blank by default.
    3. The Default value of the parameter.
      • The parameter is blank by default and only applies when the Propagate at startup option is selected.
    STEP 2: Opening the parameter setup dialog

    To set up parameters for a query, you begin with the selection of a query that contains parameters and then select the Parameters tab.

    • You click either the Value or Default cell of the parameter you want to edit.
    • The Parameter Setup dialog will open.

    Starting with the first dialog, the following options are available:

    1. Previous and Next arrow buttons can be used to browse through all the available parameters, without having to close the dialog and select another parameter.
    2. The name of the current parameter is displayed.
    3. The Source selection box provides you with the following three options to select from:
      1. Component Property – if selected, you can choose the property of a control or vector for the parameter.
      2. Constant – if selected, you can enter any alphanumeric value for the parameter.
      3. Data Element – if selected, you can browse for, or type in, any Data Element value for the parameter.
    4. The Value of the current parameter being configured and is relevant to the Source selected.
    5. The Default value used for the parameter and only applies when the Propagate at startup option is selected.
    6. The Close button will close the dialog and apply the last parameter configuration to the Database Behaviour.
    STEP 3: After all parameters have been configured

    If you have configured all the parameters correctly and no errors are displayed on the Parameters tab, you click Finish to save the behaviour.

    To edit a parameter that has already been configured.

    • Simply click on the Value or Default selection lists of the parameter you wish to edit.
    • This will launch the Parameter Setup dialog again.
