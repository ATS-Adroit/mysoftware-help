Automatic master mode assignment

In automatic mode, the systeminfo.serverMode is automatically controlled by the state of the partner server and the state of the local systeminfo.serverstate slot.

Rules and implications

  1. Starting conditions for a new cluster server.

Each server can be optionally configured to make itself master after a configurable period of time elapsed after this server has started (loaded).

When this time period has elapsed after startup, if the server has not yet detected another cluster server in that project, then it will set itself to master. If, however, it does detect other cluster servers and no master server exists in that list of servers, then it will elect itself as master if it is the lowest alphabetically named server (i.e. closest to ‘a’) in its list of healthy standby cluster servers.

  1. Consequences on the cluster of adding a new cluster server.

No automatic changes are incurred on any cluster server when adding a new server to the cluster. All cluster servers loadup as standby servers. Therefore, if a master already exists in the cluster, adding a new server will not cause an automatic master mode switch between the servers.

If it is required that a newly started server take over as master, and then the options in (4) below can be used.

  1. Consequences on the cluster of removing a cluster server.

The process of removing a server incorporates both normal program termination and abnormal program termination (software or hardware failures).

No automatic changes are incurred on any cluster server when removing a standby server from the cluster. However, when the master server is removed, the remaining healthy standby server will become master.

  1. Consequences on the cluster when changing a server’s serverMode and/or serverState slots:
  2. The serverMode slot of a healthy standby server is set to master. The server hosting this operation will first set the remote cluster server serverMode slot to standby and only then set itself to master.
  3. The serverMode slot of a healthy master server is set to standby. The server hosting this operation will not take any further action. The healthy remote standby server will detect the change and switch to master mode.
  4. The serverState slot is set from healthy to unhealthy for a standby server. The remote cluster server will not take any action.
  5. The serverState slot is set from healthy to unhealthy for a master server. The master server will simultaneously set itself as standby, so that an unhealthy master is never obtained in the cluster. The remote server will detect the change (from healthy master to unhealthy standby) and become the master server.
  6. The serverState slot is set from unhealthy to healthy for a standby server. The remote cluster server will not take any action.

An automatic election for master mode at a healthy standby server will occur when:

  • a healthy master server is removed
  • when the current healthy master server becomes unhealthy
  • the user sets the serverMode slot of a healthy standby server to master or
  • the user sets the serverMode slot of a master server to standby.

This results in a new master and the Adroit system will ensure that the existing master is relegated to standby, thereby ensuring that two master servers cannot exist in the cluster.

Suggested method of operation

Start both Agent Servers in the cluster at the same time, and then the server with the lowest alphabetical name (i.e. closest to ‘a’) will become the master server.

In an unplanned master server computer or software termination, the standby server will take over and the automatic UI’s will switch to the new master server.

If, however, a master server takeover is planned, simply set the desired standby server as master and the current master will be delegated to standby. Thereafter, the automatic UI’s will switch to the new master server.

Adding a new cluster server to the cluster will have no effect on the system. A planned takeover can be implemented either before a planned computer shutdown occurs or when the repaired computer is brought back into the cluster and is instructed, using the manual override, to take over as master.
