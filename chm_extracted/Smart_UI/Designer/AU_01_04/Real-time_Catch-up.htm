Real-time catch-up

Certain agent types on a cluster server require synchronisation of internal data structures with their Master partner.

  • This process is called real-time catch-up.
  • When a cluster partner starts up and it's Master server is available, this synchronisation takes place while the standby server is loading up.

Note:  Real-time catch-up is not associated with shadowing and datalog catch-up.

The following agent types support real-time catch-up: Analog, Digital, Counter, Expression, IOT, MaxDemand, PID, Scheduler and Statistical.

 

How the Real-time catch-up process works

The Real-time catch-up is a process that applies to clustered Agent servers only and not to stand-alone servers. The process occurs during the start up of a standby agent server, if a master agent server is already running.

If this is the case, then every agent that is loaded from the WGP file and also supports real-time catch-up will request the current state of the agent from the master server and then synchronise itself.

The WGP file is loaded in two phases:

  1. First, all the agents are loaded from the WGP file.
  2. Each agent is initialised synchronously. During this phase each agent subscribes to other agents when required by expression agents.
  3. It is during this phase that the agent will synchronise itself, using real-time catch-up with the same agent in the master agent server.

On completion of phase 2 above the agent server then enters the ready state. As an illustration of real-time catch-up:

  • Let’s assume we have an analog agent called TANKLEVEL.
  • The saved value of TANKLEVEL in the WGP file is very likely to be an old value (for example, 25%) that was relevant at the time the WGP file was last saved.
  • The current real-time value in the process is very likely to be different (let’s say 55%) from the saved value of 25%.
  • The TANKLEVEL agent in the newly started standby agent server will then synchronise its slot values with those of the master during the agent initialization phase.
  • Both servers should now reflect 55% for the TANKLEVEL.value.

Take note of following

  1. In scenarios where Adroit installations only save their WGP files after a configuration change, it is important to realise that:
    • Adroit does not automatically save WGP files on shutdown of the agent server unless it is specifically configured to do so.
    • It is then very likely that the WGP files contain old saved values which makes the requirement for real-time catch-up a very important process.
  2. Installations where a cluster is setup to extend the configuration on the standby server should execute the following procedure:
    1. Let’s call the maser server AS1 and the standby server AS2.
    2. Save the WGP file on the standby server AS2.
    3. Switch the standby AS2 to master, resulting in AS1 becoming the standby.
    4. Stop the standby agent server which is now AS1.
    5. Copy the WGP file from standby AS2 to master AS1.
    6. Restart the standby server AS1.
    7. Optionally, once AS1 is back up and running correctly, switch AS1 back to master if this is the preferred master agent server.
  3. When the synchronisation has completed, the agent server values contained in the newly copied WGP file may still be a few minutes old and will require further real-time catch-up to finalise current process values.
