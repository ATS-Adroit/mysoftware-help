1. Overview 
 
Sigfox is a Low Power Wide Area Network (LPWAN) technology that allows Sigfox enabled devices 
to send small packets of data to the Sigfox Cloud (dedicated Sigfox servers on the internet). Sigfox 
uses a very light-weight protocol, so devices consume very little power and can operate over large 
distances. 
 
As shown below, the Sigfox network consists of objects (devices), Sigfox Stations (gateways) and 
the Sigfox cloud (internet). Objects are Sigfox compliant sensors that send data over the air to the 
Sigfox base stations, which then routes the data to the Sigfox Cloud (also known as the Sigfox 
backend). The Adroit Sigfox Driver then communicates with the Sigfox cloud via an API or a call-
back, to retrieve the objects data. 
 
 
Figure 1 Sigfox Overview 
 
This Sigfox Driver document is divided into two parts: 
 Setting up and registering objects/devices onto the Sigfox cloud. 
 Setting up the Adroit Sigfox driver to communicate to the Sigfox cloud. 
 
 PLEASE NOTE 
The Sigfox cloud can store a maximum of 1 years’ worth of data per device.

3. Device Configuration 
 
3.1. 
Part 1 
 
3.1.1. Setting up Devices on the Sigfox Cloud 
Before you can register your Sigfox devices onto the Sigfox Cloud, there are two things you must 
do: 
 Make sure there is Sigfox Coverage in the area that you are deploying the devices. If there is 
no Sigfox coverage, please contact South Africa’s Sigfox Local Operator - Sqwidnet at 
https://www.sqwidnet.com/. 
 Buy a Sigfox contract and load tokens onto that contract. Each Sigfox device you are 
registering requires one token. There are three different types of contracts: 140 messages 
per day, 50 messages per day and 2 messages per day. If your device can send 140 
messages per day, then go with this contract. Similarly, if your device can only send 2 
messages per day, then go for the 2 messages/day contract. Contact your country’s Sigfox 
operator for more information on the different types of contracts and how to purchase them. 
In South Africa, please contact South Africa’s Sigfox Local Operator - Sqwidnet at 
https://www.sqwidnet.com/. 
 
 PLEASE NOTE 
If you need to register 10 devices onto a 140 messages/day contract, then you need 10 tokens 
on that 140 messages/day contract. 
 
 PLEASE NOTE 
Each device type is associated to a specific contract, so make sure it is the correct contract 
(140/50/2 messages per day).

3.1.2. Sigfox Backend Hierarchal Structure 
Figure 2 displays the hierarchal structure of the Sigfox backend, which is arranged in the following 
way: 
1. Groups: This is the highest level. For example we have an Adroit group. 
2. Sub-groups: Groups are divided into several sub-groups; we divide each customer into their 
own sub-group. 
3. Device types: Group of devices with the same behavior. All sensors that have same 
manufacturer, payload, contract and call-back will fall into the same Device Type, for example 
Device_Type_Visio_Pressure. 
4. Devices: Also known as objects, fall under a specific Device type category. They have a 
unique PAC ID, ID and a Product Certificate. For example, device_VisioPressure_123456.

3.1.5. Setting up the Sigfox Callback 
The Sigfox Callback is used to send data to a specific computer on the internet when the value of a 
device changes on the Sigfox backend. As shown in Figure 6, the callback is a query string with a 
public facing IP address (41.185.80.219) and an open port (5004) on the machine. This should be 
the IP address of the computer where Adroit is running. An example of the query string is: 
http://41.185.80.219:5004/sigfox_data?id={device}&time={time}&data={data}&snr={snr}&statio
n={station}&avgsnr={avgSnr}&lat={lat}&lng={lng}&rssi={rssi}&seqNumber={seqNumber} 
 
 PLEASE NOTE 
Your computer must have a public IP address and the port in the callback string must be opened 
on the firewall on the computer that is running Adroit.

3.3.1. Driver Details 
Enable Secondary – (Default = OFF) Allows enabling of redundant Sigfox Cloud connections such 
that in case of a failure, a switchover will occur. 
 
Primary – Allows configuration setting of the Primary Sigfox Cloud connection. 
 
Secondary – Allows configuration setting of the Secondary Sigfox Cloud connection. 
3.3.2. Primary Connection Parameters 
Enable shadow scanning from master to standby – (Default = OFF) If enabled will stop any 
communication to the Sigfox Cloud when the Agent server is in standby mode. By default, parallel 
scanning is assumed. 
 
Enable standby reads – (Default = ON) Allows reading from the Sigfox Cloud when Agent Server 
is in standby mode. 
 
Enable standby writes – (Default = OFF) Allows writing to the Sigfox Cloud when Agent Server is 
in standby mode. 
3.3.3. REST API 
User – This is the API Access Login name from the Sigfox Backend, see Figure 13. 
 
Password – This is the API Access Password from the Sigfox Backend, see Figure 13. 
 
Device type ID – The Device Type ID from the Sigfox Backend, as shown in Figure 5. 
3.3.4. HTTP Server 
Port – The port which the Sigfox Backend will use to connect to Adroit. Make sure this port is open 
on the firewall and accessible from the internet. This port must be used in the Callback query string, 
as shown in Figure 6. 
3.3.5. Script 
Script File – Load the script file to parse the Device Type payload. 
3.3.6. TimeOut 
Contact Exceeded Time – If Adroit does not receive a payload from a specific device within this 
amount of time, the device will mark bad. Due to the 140 message constraint, the minimum contact 
exceeded time is 10 minutes. A value of 0 will disable this functionality. 
 
 PLEASE NOTE 
The computer that has Adroit installed and running must have internet access. In addition, all 
relevant Sigfox ports must be accessible from the internet.

5.1. 
Final Verification 
Once this has all been completed. Power your Sigfox device and check the backend for incoming 
messages. Check the date and time to make sure the newest messages are coming in. If there are 
no new messages, then check your Sigfox network coverage, Sigfox device battery life and your 
contract (1/50/140 messages per day). 
 
 
Figure 15: Sigfox Backend Messages 
If the latest messages are coming into the Sigfox backend, then check that your Adroit Agents slots 
are being updated with the newest values. 
 
 
Figure 16: IOT Agent Slots 
 
If you are not getting the latest values into your Agent slots, then check the JavaScript file, the XML 
file, the Device ID that is scanned. The relevant ports are opened and if you have internet access to 
that machine.

then you need to register that device onto the Sigfox backend (see Part 1 of this document). If
it was registered, then check if it was deleted, moved or if you are searching in the correct
Sigfox group.
Figure 17: Device Not Found
2. Step 2 is to check if the device and device type contracts have expired. In Figure 18 below, the
adroit_t_50bb_820c contract is clickable, this is where you can check if the devices and device

Figure 18: Check Contract Validity
3. Step 3 is to check if the information on the Sigfox backend is correct for that specific device, as
shown in Figure 19 below.
Figure 19: Verify Device Payloads
If the signal strength is bad, then packets could be lost. Check the times of each message
and check if this correlates to the devices contract (140/50/2 messages per day). Also
check if the payload of these messages are what you expect, if you are unsure how to
interpret the payload, then contact Adroit support or the device manufacturer. This is the
first place to check if you are reading incorrect values in Adroit from the device.
If the timestamp is very old, and a lot of messages are being lost, then check if the device
is turned off, if the battery died or if the device moved to a location with bad signal
strength.
4. If the callbacks are failing, as shown in Figure 20 below. Then the callback URL for the device
type associated to that device might be incorrect. The port needs to be opened on the relevant
firewalls and servers and the IP address must be a static public IP address. If the Agent Server
is not running on the machine waiting for the callback, then the callback will also fail. Note that
multiple callbacks can be setup for a device type and if one of them fails (and the rest
succeed), then the icon will go red. Also make sure the User, Password and Device Type ID are
correct in the Adroit Sigfox Driver Configuration.
Figure 20: Callback Failure
