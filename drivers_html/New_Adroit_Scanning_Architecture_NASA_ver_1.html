Audience
The intended audience is communications specialists knowledgeable in protocols, and in the
hardware technologies that make data communications possible. I also assume that some terms
related to the operation of Adroit such as proxies and subscriptions make sense at a simple level
at least. A working knowledge of scanning is also assumed.
The problem
Currently we identify 2 short-comings in the Adroit scanning philosophy, these are largely offset
by simplicity of configuration, and some automated reasoning in our drivers. However for the
more advanced customer who wants total control, and the best possible performance we identify
the following.
Double-polling of data when packing in the Front-end has overlaps
Continued polling of data that is not needed in the client at times.
We will now lay out the reasons for the problems, and then move onto a proposal in the next
section. Understanding these problems is imperative to the design of a solution.
Double-polling:
This occurs because the driver always maps I/O addresses that are near to
each other into one large task. This happens automatically in the driver
based on an optimization algorithm which tries to fetch the largest legal
blocks (PDU length) of data since this is the optimal method. This causes
a hitch because of a presentation problem. For instance data in an Analog
tag in Adroit has 8-byte IEEE float presentation, data in a counter would
have 4-byte long. If I/O addresses for these 2 types is interspersed, the
driver has to create 2 tasks in order to return the data to Adroit, one for
the IEEE presentation, and another for the 4-byte long. Nothing however
stops the driver from creating one physical task for both, and converting
for both presentations (this may include Booleans and Strings) in memory,
saving communications bandwidth.
Continuous polling:
The scanning sub-system continues to poll for data even if it is not
required. The only current work-around is to create a separate device
agent for each plant segment, and scan those tags from it. Then, when
the data is not required, stop the device agent. This situation is quite
complex, and as a system grows with time, the benefits of this type of
configuration are typically eroded by people placing more un-necessary
tags on mimics, which causes these scan tasks to run again when only 1
item is needed.
Limited data types:
Currently the Adroit scanning subsystem is limited to scanning Boolean,
Integer, Real and String[80] data types only. The new architecture will
break this limitation allowing for datetime and longer strings data types to

New architecture
NASA requires changes in two areas of Adroit's scanning subsystem:
New device agent
A new Device class (called Device_NASA) inherits from the current Device class in the device agent
to handle the new architecture.
The Device_NASA class does NOT require the use of scan agents. The responsibility for scheduling
scan tasks are now demoted to the protocol driver as explained later.
The

CAdroitProtocolDriverCallbacks class which will allow NASA drivers to call back into the device

On creation of a device agent, the decision to use the legacy device class or the new class takes
place in the Device agent's construct() API call whereby the driver DLL would be tested for the
existence of a new export function called CreateAdroitProtocolDriver, otherwise falling back to
the legacy ProtDrvCreate. If CreateAdroitProtocolDriver exists, it implies that the protocol driver
is compliant to the new scanning architecture and will be controlled by an instance of
Device_NASA.
In order to cater for on demand polling, a scan flag bit mask will be introduced for each scanned
item that will denote the type of scanning required for each scanned tag. These are:
Bit 0 = enable reads
Bit 1 = enable writes
Bit 2 = output initialize
Bit 3 = demand scan
It is envisaged that write-only tags will never be marked bad.
The scanned Adroit tag type is NOT passed to the driver. The driver shall return all values as
COleVariant's and the Device_NASA class shall be responsible for converting these returned
The driver issues callback to the Device_NASA class in much the way OPC callbacks work viz an
array of tag handles, an array of timestamps, an array of variant values and an array of qualities.
New protocol drivers
Unlike the legacy architecture, where flat C DLL export functions are used to interface to the
protocol driver, NASA drivers will derive from an abstract class called CNASADevice which will
contain the necessary functions for interfacing. The interface specification is included in the file
nasadevice.h with further definitions defined in nasaclasses.h.

Cluster operations
Cluster scanning operations, such parallel scanning will now be controlled at the protocol driver
level on a device by device basis. The Device_NASA class will inform the driver of the current
agent server cluster status via a SetClusterStatus() method call and this method will return
whether the driver is configured for shadowing or not, thus instructing the device agent to
perform shadowed putslots if required.
The legacy global cluster shadowed scanning configuration will only apply to legacy architecture
protocol drivers.
Quality values
Quality values will honour the defined OPC quality values. These are currently defined as:

nasaclasses.h file
The nasaclasses.h file contains the following classes:
CAdroitProtocolDriverCallbacks Base class for Device_NASA class allowing for CNASADevice
instances to call back into the device agent
CScanItem

CAdroitOleDateTime
Helper class to the COleDateTime to provide millisecond
support
CNASAPropertyItem
Defines a single configuration property for CNASADevice's
CNASAPropertyItems
A collection of CNasaPropertyItems
nasadevice.h file
The nasadevice.h file contains the following classes:
CNASADevice
Base class for all NASA drivers. The new device class will will
contain an instance of this class as instantiated by the driver
itself
CAdroitProtocolDriverCallbacks Defines the callback that must be implemented by Adroit's
Deicve agent to allow NASA drivers to process new values from
the FED.

Troubleshooting Performance Counters
To test if performance counters are active, goto permon.cpp line ~456 and change the
perfversion, this tells the setup procedure to reinstall performance counters, this is especially
important if performance counters are ADDED even if it is just a name change when including the
use of a new "USERx" count.
Perfmon.cpp:
CHAR perfversion[] = "1.00";
After compile rerun setup.
Any name change you must rerun incs.bat, and you cannot transfer incs between projects.
Another check is via regedit:
HKEY_LOCAL_MACHINE\SYSTEM\CurrentControlSet\Services\D_SAMPLE_NASA
