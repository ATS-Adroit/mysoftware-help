Overview
Supports OPTOMUX slave digital and analog controllers. Each OPTOMUX board consists of a brain
board with microprocessor and an I/O mounting rack. The units communicate over a RS422/485 network
which interfaces to the computer via an interface converter.
This document refers to the microprocessor and I/O rack as the remote module.

Local Details
Port - The available serial ports on your machine
Retry - The number of times that Adroit will try to gain communication with a module before failing a
transaction.
Timeout - The time that Adroit will wait for a valid response from a module before failing a transaction
(Read or Write).
Parity - Default to none.
Data Bits - Default to 8.
Stop bits - Default to 1.
Controllers… - Configure the controller specific start-up procedures and initialization.
Modules… - Configure which controllers are enabled.
Moxa Cluster Support - Check this option when running on a MOXA virtual port in a cluster
environment. It will allow to purge the port when in standby and in shadow mode, as the MOXA unit stops
functioning in this mode. Data keeps filling the buffer seeing that the driver does not do any reading from
the port and eventually becomes unresponsive!
Hard Purge (Using API) - Does a call to the COM PORT to purge all the data on it. (Preferred Method).
Soft Purge (Read from Port) - Continue to read data from the port and just discard it.
Close serial port on fail - With a transaction failure closes the port and re-opens it by default but for some
virtual ports it becomes an issue so we allow not closing the port in this case.

General Addressing structure
Remote I/O items are addressed by specifying the type of item (analog in/out, digital in/out), the address of
the module (0-255) and the position or offset in that module. Valid I/O positions are 0 through 15.
Addressing is in decimal.
Addresses are specified as follows:

Modules are addresses by 'M' for module, followed by the controller address, the module type, then it's
position from 0(zero) to 15.
Digital I/O can be scanned into a multistate, by specifying the first digital module in the controller, as input
or output, if output is used, all positions will become outputs. When writing to the value, only the output
modules on the board get updated.
as scan points.
All non-configured positions are assumed by the driver to be inputs.
The special address mnemonic for a Boolean or Digital slot is supplied to initiate configuration refresh
on demand: "UPDATE". Issuing a digital write with a value of 1 will initiate steps 2 & 3 of the startup
sequence described in Operation. This address will return zero if scanned. This will refresh the
configuration of all the enabled controllers.
The special address mnemonic "ENABLE n" will allow enabling and disabling of scanning for a
specific module "n", as an enable tag. This virtual variable can also be driven from the driver setup
dialog. If the dialog is used to change the value, the digital tag (if scanned) associated with the variable
will also update. A value of 1 = enabled, and zero (checkbox off) = disabled.
The enable tags get saved in the system registry database for each device, if the device gets deleted in
the setup program, this information is thus lost.

Operation
The driver scans all input and output variables as required by the scan agents. When writing, the driver only
writes to items configured as outputs. Digitals are written using read-mask-write. On the relevant start-up
flag the driver will upload all settings, a dummy force tag is also provided to allow refreshing of the
configuration data. Start-up flags triggered by events are controller start-up and driver loading, providing 3
ways to refresh the controller configuration.
The controller configuration is controlled by the driver, which uses the complete I/O list of scan-points to
configure the controller I/O points. If 2 scanned points for the same I/O module have conflicting
information, the last one's configuration will be used. Since which ever scan point is the overriding one is
not configurable, this technique is advised against. The figure below illustrates the possible ways to
initialize the controller configuration.
Start-up involves 3 steps:
1. Clear power-on flag (in event of power on).
2. Set Turn-around delay, watchdog and protocol type parameters.
3. Send all I/O configuration information to the controller.
All Opto22 controller I/O configuration data will be derived from actual scanning configured in the adroit
database, so as a new scan-point gets configured it will be down-loaded to the controller. Already
configured scan points all get sent immediately when the scanning starts (i.e. device starts) as the system
loads.
Multiple devices
Multiple devices may not be assigned to scan the same controller, else the I/O configuration information
which is down-loaded will conflict. If multiple devices are used to address the boards on a single line, they
must be uniquely assigned to scan the boards.

To scan boards on a separate line, a new device must be assigned to that line, the above rule will not apply
to devices on separate communication ports or lines.
Tag scaling configuration
Opto22 modules provide a raw output range of 0-4095, the actual value derived to the SCADA is biased
with a constant value of 4096, thus the raw range of an analog is 4096 to 8192. Missing modules and
modules not already configured in the scanning database, will return 0 (zero). All slots in a module, which
are not configured, are assumed to be inputs.

Enable tag saving
The enable tags for the modules are saved in the registry, if the Setup program or the agent server does not
have the required security to change the registry, the changes will not be transferred and saved. Change the
security on the registry key or log-on as a different user to run Setup or the Agent server. Making the
registry key
read-only will stop the saving of the tags, but still allow operator actions on them, these can then be
disabled using menu security and putting a password level on the operator actions.
Starting & stopping scanning
From adroit version 407 onwards we have implemented a start-stop signal to the driver for polled drivers,
this driver will thus not operate correctly with versions prior to build 407.
Performance
Typical performance indicates over 20 polls per second can be executed, i.e. with 10 modules, the cycle
time is approximately 500ms.
If Analog input and output modules are used together, the output modules should be scanned more slowly,
since they are polled separately due to protocol differences, this means 2 scans for the one controller, not
just one.
