About Alarm Acknowledgement

Acknowledgment is typically recommended for alarms or incidentssignified by AgentName.AlarmType, which indicate that this agent has gone into the condition or state specified by this alarm type. Each incident can either be an alarm (requiring action) or an event (not requiring action). that require some sort of reaction or attention from the operator.

In other words, an alarm should be any event that an operator must understand, acknowledge and respond to – and not simply acknowledge and ignore.

Therefore you should carefully consider, which incidents require acknowledgement and which do not. Adroit provides the following methods of acknowledging alarms:

  • Global acknowledgement: This should be used when using a standalone Adroit installation or for those alarms that only one operator needs to be made aware of.

    By globally acknowledging an alarm from any computer in the network, this incident will be removed from ALL the lists in the system (provided, of course, that the alarm is no longer active).

  • Local acknowledgement: This should be used when you have alarms that more that one operator needs to be aware of. Click for more details:

    In other words you have a distributed Adroit installation, with operators viewing the process from remote user interfaces.

    Local acknowledge refers to the action of acknowledging an alarm in an alarm list of an AlarmList agent. This removes the alarm from this alarm list, provided the alarm is no longer active. 

    If the alarm is routed to other alarm lists (usually on other computers), locally acknowledging the alarm one alarm list will not clear the alarm from these other alarm lists.

    This method therefore requires that each operator locally (remotely) acknowledges the alarm, to remove it from their alarm list (once it is no longer activethe monitored condition of this incident (alarm/event) is still in effect and has not yet returned to its normal operating state.).

    Note1: In the case of local alarm acknowledgement, you need to use the AlarmList agent to contain these incidents and NOT the Alarm agent. For further details of using AlarmLists and displaying alarms, see Displaying Alarms.

    Note2: Once an incident has been locally (remotely) acknowledged from a remote UI, the color of this alarm changes (to blue by default) so that the other operators can see that this has occurred. However, each operator that views this alarm still needs to locally acknowledge it before it is removed from the list.

    Only when this alarm is globally acknowledged is it removed from the global alarm list of the Alarm agent.

For more details about enabling or disabling the acknowledgement of incidents, see Configuring Incident Acknowledgement.

For details about acknowledging alarms using the Alarm List Viewer window, see Acknowledging Alarms.

Note: To define how the alarming subsystem treats current alarms if an agent’s statusalarmInhibit slot is set to one and the agent is currently in alarm and/or unacknowledged, add and configure the SmartInhibit registry value.

If you route incidents to an AlarmManagement agent, then instead of operators simply acknowledging an incident, by pressing a button, you can have them:

  • specify the reason and sub-reason that caused this incident and/or
  • specify additional notes relating to this incident.

These measures will improve your incident reviews.

You can also have your operators launch a HTML document relating specifically to each incident to help them both UNDERSTAND and RESPOND appropriately to this incident.  

For details of how to use the AlarmManagement agent, see Quick Start to Configure and Record Incidents (Alarms/Events).

 

For details about hiding or showing the local and/or global acknowledgement buttons of the Alarm List Viewer window, see Securing Acknowledge Buttons in Alarm Windows.
